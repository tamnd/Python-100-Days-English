## RESTful Architecture and DRF Basics

SOA, or service-oriented architecture, can be implemented in many ways, including RPC, Web Services, and REST. At the business level, SOA emphasizes reuse and interoperability. Among those implementation styles, REST is widely regarded as the best fit for internet applications, and an architecture that follows REST constraints is often called RESTful.

### What REST Means

REST stands for **Representational State Transfer**. The term was introduced by Roy Fielding in his 2000 doctoral dissertation.

To be more precise, the "representation" in REST refers to the representation of a resource. A resource is a concrete piece of information on the network, and the URI identifies that resource rather than its specific representation. The client performs state transitions on the server by operating on those resources through HTTP.

Core ideas:

- every URI identifies a resource
- resources can have multiple representations such as HTML, XML, JSON, or binary data
- HTTP methods express operations on resources

Typical REST-style URI patterns:

| HTTP Method | URI | Meaning |
| --- | --- | --- |
| `GET` | `/students/` | List all students |
| `POST` | `/students/` | Create a student |
| `GET` | `/students/ID/` | Retrieve a student |
| `PUT` | `/students/ID/` | Replace a student |
| `PATCH` | `/students/ID/` | Partially update a student |
| `DELETE` | `/students/ID/` | Delete a student |
| `GET` | `/students/ID/friends/` | List a student's friends |
| `DELETE` | `/students/ID/friends/ID/` | Remove a friend relationship |

REST is not just about URI style. Statelessness and idempotency are also important, and those deeper points matter just as much as the shape of the URI.

### Installing and Configuring DRF

In Django, the most popular REST toolkit is `djangorestframework`, usually called DRF.

Install it:

```bash
pip install djangorestframework
```

Add it to `INSTALLED_APPS`:

```python
INSTALLED_APPS = [
    'rest_framework',
]
```

You can also configure defaults such as:

- page size
- pagination class
- exception handler
- parsers
- throttling
- permissions
- authentication

### Serializers

Separated frontend-backend development usually means JSON APIs, and JSON APIs require serialization.

Example serializer:

```python
from rest_framework import serializers 


class SubjectSerializer(serializers.ModelSerializer):

    class Meta:
        model = Subject
        fields = '__all__'
```

### Function-Based API View

DRF supports both function-based views (FBV) and class-based views (CBV). A simple FBV example:

```python
from rest_framework.decorators import api_view
from rest_framework.response import Response


@api_view(('GET', ))
def show_subjects(request):
    subjects = Subject.objects.all().order_by('no')
    serializer = SubjectSerializer(subjects, many=True)
    return Response(serializer.data)
```

This is more concise than manual JSON conversion and automatically integrates with DRF’s browsable API.

### Teacher API

Teacher serializer:

```python
class SubjectSimpleSerializer(serializers.ModelSerializer):

    class Meta:
        model = Subject
        fields = ('no', 'name')


class TeacherSerializer(serializers.ModelSerializer):

    class Meta:
        model = Teacher
        exclude = ('subject', )
```

Teacher endpoint:

```python
@api_view(('GET', ))
def show_teachers(request):
    try:
        sno = int(request.GET.get('sno'))
        subject = Subject.objects.only('name').get(no=sno)
        teachers = Teacher.objects.filter(subject=subject).defer('subject').order_by('no')
        subject_seri = SubjectSimpleSerializer(subject)
        teacher_seri = TeacherSerializer(teachers, many=True)
        return Response({'subject': subject_seri.data, 'teachers': teacher_seri.data})
    except (TypeError, ValueError, Subject.DoesNotExist):
        return Response(status=404)
```

The frontend can then render those results using Vue.js.

### Token-Based Login in Frontend-Backend Separation

Traditional session-based login stores state on the server. In horizontally scaled systems, that makes synchronization harder. A common alternative is token-based tracking.

Typical flow:

1. User logs in successfully.
2. Server returns a token containing user identity and expiration info.
3. Frontend stores the token in `localStorage`, `sessionStorage`, or another client-side store.
4. Every API request sends the token in the HTTP headers.
5. If the token is missing, invalid, or expired, the server returns `401`.
6. The frontend redirects the user back to the login page.

JSON Web Token (JWT) is one of the most common implementations of this idea.

At a high level, a JWT is composed of three parts joined by dots: the header, the payload, and the signature. The header describes the token type and signing algorithm, the payload stores claims such as user identity and expiration, and the signature protects the token against forgery and tampering.
