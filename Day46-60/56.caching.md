## Using Caching

In many web systems, the main performance bottleneck is the relational database. When concurrency grows, sending every request directly to the database becomes expensive. One of the most important ways to improve performance is to cache high-frequency, relatively small data sets.

This is the classic tradeoff of space for time.

Redis is a common choice because it stores data in memory and uses very efficient storage and access strategies such as hash-based storage and key-value access, so its read and write performance is far better than that of a relational database.

### Connecting Django to Redis

The lesson uses `django-redis`:

```bash
pip install django-redis
```

Configure Django caching:

```python
CACHES = {
    'default': {
        'BACKEND': 'django_redis.cache.RedisCache',
        'LOCATION': ['redis://1.2.3.4:6379/0', ],
        'KEY_PREFIX': 'vote',
        'OPTIONS': {
            'CLIENT_CLASS': 'django_redis.client.DefaultClient',
            'CONNECTION_POOL_KWARGS': {
                'max_connections': 512,
            },
            'PASSWORD': 'foobared',
        }
    },
}
```

### View-Level Caching

#### Declarative caching

For function-based views:

```python
from django.views.decorators.cache import cache_page


@api_view(('GET', ))
@cache_page(timeout=86400, cache='default')
def show_subjects(request):
    queryset = Subject.objects.all()
    data = SubjectSerializer(queryset, many=True).data
    return Response({'code': 20000, 'subjects': data})
```

This caches the entire response for one day.

For class-based views, use `method_decorator`:

```python
from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_page


@method_decorator(decorator=cache_page(timeout=86400, cache='default'), name='get')
class SubjectView(ListAPIView):
    queryset = Subject.objects.all()
    serializer_class = SubjectSerializer
```

#### Programmatic caching

You can interact with Redis more directly:

```python
def show_subjects(request):
    redis_cli = get_redis_connection()
    data = redis_cli.get('vote:polls:subjects')
    if data:
        data = json.loads(data)
    else:
        queryset = Subject.objects.all()
        data = SubjectSerializer(queryset, many=True).data
        redis_cli.set('vote:polls:subjects', json.dumps(data), ex=86400)
    return Response({'code': 20000, 'subjects': data})
```

This is more flexible than declarative caching, but it also requires you to manage serialization and cache keys yourself.

Django also provides ready-made `cache` and `caches` objects to support cache operations. The former accesses the default cache and the latter can be indexed to access a named cache service such as `caches['default']`. Sending `get` and `set` messages to the cache object is enough for basic reads and writes, but direct Redis access is still more flexible. At the same time, because a raw Redis connection can issue dangerous commands such as `FLUSHDB` or `SHUTDOWN`, real projects often wrap `django-redis` one more time and expose only the cache operations the project actually needs.

### Cache Update Strategies

The lesson covers three common patterns:

1. Cache Aside
2. Read/Write Through
3. Write Behind

The most common practical choice is Cache Aside:

- update the database first
- then delete the cache entry

You should not update the database and then update the cache, and you should not delete the cache first and then update the database. Under concurrent reads and writes, both of those approaches can create consistency problems. Even the database-first-then-delete-cache strategy is not theoretically perfect, but in practice the probability of failure is very low, which is why many projects use it.

`Read Through` and `Write Through` push more of the cache-maintenance work into a storage abstraction so the application sees only one storage interface. `Write Behind` updates the cache first and pushes changes to the database asynchronously in batches. That can improve performance a lot, but it gives up strong consistency and is more complex to implement because the system has to track what changed and flush it later.

### Cache Penetration, Breakdown, and Avalanche

#### Cache penetration

Requests repeatedly target data that does not exist in the cache or database, sending all pressure to the database.

Possible fixes:

- cache null results for a short time
- use a Bloom filter

#### Cache breakdown

A very hot key expires, and many concurrent requests hit the database at once.

Typical solution:

- use a mutex lock, such as `SETNX`, so only one request rebuilds the cache

#### Cache avalanche

Many keys expire at the same time, causing a flood of database traffic.

Typical solutions:

- add random jitter to expiration times
- use multi-level caching
