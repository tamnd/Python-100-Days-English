### Preparing for Login

1. Create a user model.

```python
class User(models.Model):
    """User"""
    no = models.AutoField(primary_key=True, verbose_name='ID')
    username = models.CharField(max_length=20, unique=True, verbose_name='Username')
    password = models.CharField(max_length=32, verbose_name='Password')
    tel = models.CharField(max_length=20, verbose_name='Mobile Number')
    reg_date = models.DateTimeField(auto_now_add=True, verbose_name='Registration Time')
    last_visit = models.DateTimeField(null=True, verbose_name='Last Login Time')

    class Meta:
        db_table = 'tb_user'
```

```python
import hashlib


def gen_md5_digest(content):
    return hashlib.md5(content.encode()).hexdigest()
```

The form includes `{% csrf_token %}` to prevent CSRF attacks. Without it, Django rejects the submission with a `403` response unless CSRF protection is explicitly disabled.

### User Tracking

Web applications usually need to remember who the user is. This is called user tracking or session management.

The server can store user information in a session object. But HTTP itself is:

- connectionless
- stateless

So the browser must send some identifier that lets the server find the right session.

Common approaches:

1. URL rewriting
2. hidden form fields
3. browser-side storage such as cookies, `localStorage`, `sessionStorage`, or IndexedDB

Cookies are the classic solution. The browser stores a small key-value record and automatically sends it back with each request to the same site. If the cookie contains a session ID, the server can locate the corresponding session object.

In short:

- server creates a session object
- server writes the session ID to a cookie
- browser sends the cookie on later requests
- server retrieves the session object and restores user state

### Django Session Support

Django enables `SessionMiddleware` by default. Because of that, every request object has a `session` attribute that behaves like a dictionary.

By default, Django serializes session data and stores it in a relational database. Modern Django versions use JSON serialization instead of Pickle, mainly for security reasons. That means session data must be JSON-serializable.

In real projects, storing sessions in a database is often not ideal because the database can become a bottleneck. Later lessons show how to move session storage into a cache such as Redis.

### Captcha and Login Validation

Generate a random captcha code:

```python
import random

ALL_CHARS = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ'


def gen_random_code(length=4):
    return ''.join(random.choices(ALL_CHARS, k=length))
```

The original lesson also includes a captcha image generator based on Pillow. The implementation is longer, but the core idea is straightforward: generate a random verification code, draw it as an image, add interference such as noise or curves, and then return the image bytes to the browser.

Once login succeeds, the typical flow is:

- verify the username and password
- verify the captcha
- write user information such as `userid` into `request.session`
- optionally update `last_visit`
- redirect the user back to the page they intended to access

At that point, subsequent requests can check whether the session contains the login marker.

### Session Support in Practice

Because `request.session` behaves like a dictionary, the common pattern after successful login is to store a key such as `userid` or `username` in the session and then check for it in later requests. Combined with the session ID stored in the browser cookie, that allows the server to remember that the user has already authenticated.
