## Software Testing and Automated Testing

### Overview of Software Testing

Software testing is a process used to help verify the correctness, completeness, security, and quality of software. In other words, it is the process of operating a program under specified conditions to discover errors, measure quality, and evaluate whether the software meets its design requirements.

#### Testing Methods

There are two classic testing methods.

**Black-box testing** focuses on the functions of an application rather than its internal structure or implementation. The tester does not need to know the application code, internal structure, or programming language in detail. The tester only needs to know what the system is supposed to do, so that a given input should produce a corresponding output. Test cases are designed from specifications, requirements, and expected functionality. This style is suitable for many kinds of testing, especially integration testing and system testing.

**White-box testing** focuses on the internal structure and execution of the application rather than just its external behavior. In white-box testing, test cases are designed from the point of view of the program logic. The tester verifies the flow of data through the code and checks whether the correct outputs are produced.

Because time and cost are always limited, one of the most important questions in software testing is:

**Among all possible test cases, which subset can discover the most errors?**

For that reason:

- white-box testing pays attention to logic coverage, such as statement coverage, condition coverage, and branch coverage;
- black-box testing often uses methods such as equivalence partitioning, boundary-value analysis, cause-effect graphs, and error guessing.

#### Types and Stages of Testing

The lesson highlights several major testing stages:

**Unit testing** checks the smallest software units, usually functions or methods, to verify their correctness.

**Integration testing** assembles modules according to an integration strategy and verifies whether the interfaces and combined behavior work correctly.

**System testing** includes broader verification such as functional testing, interface testing, reliability testing, usability testing, and performance testing.

**Regression testing** is testing done to detect errors introduced by code changes. It is especially important in maintenance work. Some studies even show that regression testing can account for more than one third of the overall cost across the software lifecycle.

#### Test-Driven Development

Test-driven development includes three steps:

1. Write an automated test for a new feature or improvement that has not yet been implemented.
2. Write the minimum amount of code needed to pass the test.
3. Refactor the code until it reaches the required quality standard.

The benefit of TDD is that it helps prevent regression and often produces higher-quality code. The lesson also reminds readers that acceptance testing should be performed by customers. A feature that passes unit tests and even system tests may still fail customer acceptance if it does not satisfy real usage scenarios.

#### Testing Internet and Mobile Applications

For internet applications, the lesson suggests thinking about testing from three layers:

1. **Presentation layer** testing, including content, site structure, and user environment such as browsers and operating systems.
2. **Business layer** testing, including performance, data validation, transactions, and external services.
3. **Persistence layer** testing, including response time, data integrity, and fault tolerance.

For mobile applications, two common strategies are:

1. testing on real devices;
2. testing on emulators.

### Unit Testing

Python’s standard library provides the `unittest` module for writing unit tests. The lesson recommends using [pytest](https://docs.pytest.org/en/latest/) or `nose2` to run tests, because they can automatically discover tests and produce clearer error reports.

Two other useful tools mentioned in the lesson are:

- [`testfixtures`](https://pypi.org/project/testfixtures/), which provides helpers for directories, system dates, mock objects, and other test setup tasks;
- [`mock`](https://pypi.org/project/mock/), which replaces dependencies with virtual objects whose return values and exceptions can be controlled during testing.

The lesson also recommends `tox` for preparing test environments. `tox` can create multiple virtual environments, run tests inside them, and unify tool options and environment variables, so a single `tox` command can drive the whole testing workflow.

### Automated Testing

#### UI Automation Testing

The lesson breaks UI automation into three parts:

- **Desktop**: [PyAutoGUI](https://pyautogui.readthedocs.io/en/latest/)
- **Mobile**: [Appium](http://appium.io/)
- **Web**: [Selenium](https://docs.seleniumhq.org/)

Selenium is introduced as a browser-driven testing toolset for web functional testing and integration testing. Like a real browser user, Selenium can click, type into forms, and verify values, which makes it suitable for converting manual operations into automated ones.

The lesson lists some Selenium advantages:

1. Test cases can be made relatively easily with Selenium IDE.
2. It supports multiple browsers and operating systems.

It also mentions several Selenium components:

- Selenium IDE
- Selenium Remote Control
- Selenium WebDriver

#### Working with Continuous Integration

The lesson connects automated testing with continuous integration. CI means integrating code into the main branch frequently. Its main benefits are:

1. errors are discovered quickly;
2. branches are less likely to drift far away from the main line.

The core idea is that code should not be integrated unless automated tests pass. In this sense, automated testing is not just a QA tool, but part of the development pipeline itself.

The lesson uses Jenkins as an example and notes that Selenium-generated HTML test suites can be integrated through the Seleniumhq plugin and corresponding Jenkins job configuration.

It also mentions other web-testing options besides Selenium:

- [WebTest](https://pypi.org/project/WebTest/)
- [Splinter](https://splinter.readthedocs.io/en/latest/)
- [Robot Framework](https://robotframework.org/)

#### API Testing Automation

For API-level automation, the lesson lists:

1. [requests](https://cn.python-requests.org/zh_CN/latest/)
2. [HttpRunner](https://docs.httprunner.org/)
3. [PyRestTest](https://github.com/svanoort/pyresttest)

#### Other Automated Testing Tools

The lesson also briefly mentions:

- [Locust](https://www.locust.io/) for performance testing;
- [PytheM](https://github.com/m4n3dw0lf/PytheM) for security-related testing work.

### Summary

The central message of this lesson is that testing is not one isolated step added at the end. It includes black-box and white-box thinking, multiple testing stages, automated execution, CI integration, and different tools for unit, UI, API, performance, and broader quality checks. Automated testing does not replace careful thinking, but it makes disciplined testing repeatable and scalable.
