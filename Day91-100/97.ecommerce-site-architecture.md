## Key Technical Points of E-Commerce Websites

### Business Models

The lesson begins with several common e-commerce business models:

1. **B2B**: business to business. Both parties are companies. Alibaba is a typical example.
2. **C2C**: consumer to consumer. Examples include Taobao and Renrenche.
3. **B2C**: business to consumer. Examples include Vipshop and Jumei.
4. **C2B**: consumer to business. Consumers first raise demand, and businesses organize production around it.
5. **O2O**: online to offline. Offline business opportunities are connected with the internet, making the internet a platform for offline transactions.
6. **B2B2C**: business to business to consumer. Tmall and JD are common examples.

### Requirement Highlights

The lesson divides requirements into the user side and the admin side.

#### User Side

1. **Homepage**
   Product categories, banner rotation, scrolling news, waterfall loading, recommendations, discounts, hot-selling products, and so on.

2. **User-related features**
   Login, third-party login, registration, logout, and self-service functions such as profile editing, browsing history, shipping addresses, and similar items.

3. **Product-related features**
   Categories, lists, product details, search, hot searches, search history, add to cart, favorites, follows, reviews, and more.

4. **Shopping cart**
   Viewing, editing quantities, removing goods, and clearing the cart.

5. **Orders**
   Submitting orders and making payment, viewing order history, checking order details, and writing order reviews.

#### Admin Side

1. CRUD for core business entities.
2. Scheduled tasks, both periodic and non-periodic, such as handling unpaid orders or raising alarms for abnormal events.
3. Reporting functions, including Excel/PDF import and export and frontend chart display.
4. Permission control, such as RBAC, white lists, and black lists.
5. Business workflows, such as refund processes.
6. Third-party services, such as maps, SMS, logistics, payment, identity verification, weather, monitoring, and cloud storage.

### Third-Party Login

Third-party login means authenticating users through accounts from outside platforms, usually large social platforms such as QQ, Weibo, Google, or Facebook. Most third-party login systems use the [OAuth](https://en.wikipedia.org/wiki/OAuth) protocol, usually OAuth 2.0.

The lesson explains the difference between a **token** and a **password**:

1. A token is short-lived and expires automatically, while a password is usually long-lived.
2. A token can be revoked by the data owner, while a password usually is not revoked by others.
3. A token has a limited permission scope, which makes it safer than giving full password access.

#### OAuth 2.0 Authorization Flow

The lesson summarizes the OAuth flow like this:

1. The user opens the client, and the client asks for authorization.
2. The user agrees to authorize the client.
3. The client uses that authorization to request an access token from the authorization server.
4. After authenticating the client, the authorization server issues the token.
5. The client uses the token to request resources from the resource server.
6. The resource server verifies the token and then returns the resource.

![](./res/oauth2.png)

In a real e-commerce application, third-party login is usually followed by account binding or automatic account association using information returned by the third-party platform.

### Cache Warm-Up and Query Caching

#### Cache Warm-Up

Cache warm-up means loading data into cache when the server starts so the first real user requests do not have to build the cache from scratch. The lesson gives an example using a custom `AppConfig` and the `ready()` method in Django to preload province data into cache.

```python
import pymysql

from django.apps import AppConfig
from django.core.cache import cache

SELECT_PROVINCE_SQL = 'select distid, name from tb_district where pid is null'


class CommonConfig(AppConfig):
    name = 'common'

    def ready(self):
        conn = pymysql.connect(host='1.2.3.4', port=3306,
                               user='root', password='pass',
                               database='db', charset='utf8',
                               cursorclass=pymysql.cursors.DictCursor)
        try:
            with conn.cursor() as cursor:
                cursor.execute(SELECT_PROVINCE_SQL)
                provinces = cursor.fetchall()
                cache.set('provinces', provinces)
        finally:
            conn.close()
```

The main idea is simple: when the application starts, query the required data and push it into the cache before traffic arrives.

#### Query Caching

The lesson also shows a custom decorator for caching query results.

```python
from pickle import dumps, loads

from django.core.cache import caches

MODEL_CACHE_KEY = 'project:modelcache:%s'


def my_model_cache(key, section='default', timeout=None):
    """Decorator for model-result caching."""

    def wrapper1(func):
        def wrapper2(*args, **kwargs):
            real_key = '%s:%s' % (MODEL_CACHE_KEY % key, ':'.join(map(str, args)))
            serialized_data = caches[section].get(real_key)
            if serialized_data:
                data = loads(serialized_data)
            else:
                data = func(*args, **kwargs)
                cache.set(real_key, dumps(data), timeout=timeout)
            return data
        return wrapper2
    return wrapper1
```

This kind of caching is useful for frequently requested hot data.

### Shopping Cart Implementation

The lesson asks an important practical question:

**Where should the shopping cart live for logged-in users, and where should it live for users who are not logged in?**

It provides a simple object model:

```python
class CartItem(object):
    """An item in the shopping cart."""

    def __init__(self, sku, amount=1, selected=False):
        self.sku = sku
        self.amount = amount
        self.selected = selected

    @property
    def total(self):
        return self.sku.price * self.amount
```

```python
class ShoppingCart(object):
    """Shopping cart."""

    def __init__(self):
        self.items = {}
        self.index = 0

    def add_item(self, item):
        if item.sku.id in self.items:
            self.items[item.sku.id].amount += item.amount
        else:
            self.items[item.sku.id] = item
```

For logged-in users, the cart can be stored in the database, optionally with Redis as a cache layer. For users who are not logged in, the cart can be stored in cookies, `localStorage`, or `sessionStorage` to reduce server-side memory pressure.

### Summary

This lesson is a compact architecture checklist for e-commerce systems. It covers business models, user and admin requirements, SPU/SKU modeling, third-party login, caching, shopping-cart persistence, and payment integration. The deeper point is that e-commerce systems are not just “websites that sell goods”; they are systems where account identity, hot traffic, transactional data, and external platforms all meet in one place.
