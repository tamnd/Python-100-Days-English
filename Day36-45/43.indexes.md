## Indexes

Indexes are one of the most important tools for improving query performance in relational databases. They are similar to a book's table of contents. Without a table of contents, finding a topic in a long book can be painfully slow because you have to scan page by page.

Creating indexes takes extra storage space, but the reduction in query time is usually worth it.

All MySQL column types can be indexed. In InnoDB on MySQL 8.0, the main index types are:

- B+ tree indexes
- full-text indexes
- R-tree indexes

Here we focus on B+ tree indexes, which are the most widely used. B+ trees are balanced trees and are very efficient for disk-based large-scale storage and sorting. A B+ tree with height 3 or 4 can hold millions or even billions of records, and finding one record may take only 3 or 4 I/O operations.

A B+ tree has:

- a root node
- internal nodes
- leaf nodes

The leaf nodes store sorted data. Because index records are ordered, binary search is efficient inside a leaf page.

When a table is created, the primary key automatically gets an index. In InnoDB, the table itself is physically organized by the primary key. That primary-key index is called the **clustered index**.

A table can have only one clustered index. Any indexes you create yourself are **secondary indexes** or **non-clustered indexes**. Secondary indexes usually store the primary key value, so after finding a matching entry MySQL may still need to go back to the clustered index to fetch the full row. This is called a **table lookup** or "back to table" access, and it is one reason why clustered index access is often faster.

Suppose we frequently search students by name. We can inspect the execution plan with `explain`:

```SQL
explain select * from tb_student where stuname='Lin Zhennan'\G
```

Without an index, the key part of the plan looks like this:

- `type: ALL`
- `key: NULL`
- `rows: 11`

That means a full table scan.

Important fields in an execution plan:

1. `select_type`: query type such as `SIMPLE`, `PRIMARY`, `UNION`, `SUBQUERY`, or `DERIVED`.
2. `table`: the table involved.
3. `type`: access type, such as `ALL`, `index`, `range`, `ref`, `eq_ref`, `const`, or `NULL`.
4. `possible_keys`: indexes MySQL could use.
5. `key`: the index MySQL actually uses.
6. `key_len`: the length of the used index.
7. `rows`: estimated rows scanned.
8. `extra`: additional details such as `Using filesort`, `Using index`, `Using temporary`, or `Using where`.

Create an index on the student name:

```SQL
create index idx_student_name on tb_student(stuname);
```

Now inspect the plan again:

```SQL
explain select * from tb_student where stuname='Lin Zhennan'\G
```

The query changes from full scan to indexed lookup, and the estimated row count becomes much smaller.

MySQL also supports prefix indexes, which index only the first `N` characters of a string:

```SQL
create index idx_student_name_1 on tb_student(stuname(1));
```

This saves space, but it is less selective. If two students share the same first character in their names, MySQL will still need to examine more rows.

Drop an index:

```SQL
alter table tb_student drop index idx_student_name;
```

or

```SQL
drop index idx_student_name on tb_student;
```

MySQL also supports composite indexes and, in newer versions, functional indexes. A well-designed composite index can enable **index coverage**, which avoids extra sorting and table lookups and can greatly improve performance.

General index design rules:

1. The best candidates for indexing usually appear in `where` clauses and join conditions.
2. Higher cardinality columns benefit more from indexes.
3. Prefix indexes can save space, but may reduce precision.
4. More indexes are not always better. Indexes speed up reads but slow down inserts, updates, and deletes because the indexes themselves must also be maintained.
5. In InnoDB, secondary indexes store primary key values, so choose a short primary key type whenever possible.

One final note: B-tree indexes in InnoDB are effective not only for equality checks on numeric columns, but also for range comparisons such as `>`, `<`, `>=`, `<=`, `between ... and ...`, and `<>`. For string columns, indexes can also be used for prefix searches such as `like 'abc%'`, but searches that start with a wildcard typically prevent index usage and may lead to full table scans.
