### Views

A view is an object in a relational database that packages the result set of a query into a queryable table-like structure. Put simply, a view is a virtual table. Unlike a physical table, which is an entity structure, a view is a virtual structure. You can also think of a view as a named SQL statement stored in the database.

Benefits of views:

1. They can hide the underlying table structure and expose only the fields the outside world needs.
2. In most cases they are read-only, which reduces the chance of direct accidental updates.
3. They let you reuse complex SQL statements.
4. They can reshape or format data differently from the physical table.

Create a view:

```SQL
create view `vw_emp_simple`
as
select  `eno`,
        `ename`,
        `job`,
        `dno`
  from  `tb_emp`;
```

> **Tip**: Because a view does not contain data, every use of the view requires the underlying query to be executed again. If the view is built from joins or nested queries and becomes fairly complex, you may find that performance drops sharply. So before using a complex view in a real application, you should test it to make sure the performance is acceptable.

With the view above, we can use the DCL statements from the previous lesson to limit some users to reading employee information only through the view. In that case, sensitive columns such as salary (`sal`) and allowance (`comm`) in the employee table will not be exposed. The code below demonstrates how to query data from the view.

```SQL
select * from `vw_emp_simple`;
```

Not every view is updatable. The following types are generally not updatable:

1. Views using aggregate functions, `distinct`, `group by`, `having`, `union`, or `union all`.
2. Views whose `select` clause contains subqueries.
3. Views built on top of other non-updatable views.
4. Views whose `where` clause contains subqueries referencing tables in the `from` clause.

Drop a view:

```SQL
drop view if exists `vw_emp_simple`;
```

> **Note**: If you want to update a view definition, you can delete the view first with the command above, or use `create or replace view`.

Rules and limitations:

1. Views can be nested and joined with tables.
2. A view may contain `order by`, but an outer `order by` can override it.
3. Views do not have their own indexes, and they do not trigger indexes or caching behavior like physical tables.

### Functions

MySQL functions are broadly similar to Python functions because both are used to package relatively independent code that will be reused. If you insist on highlighting a difference, one is that MySQL functions can be declared to read data through SQL statements. In the example below, we define a function that truncates an overlong string.

The following function truncates a long string:

```SQL
delimiter $$

create function fn_truncate_string(
    content varchar(10000),
    max_length int unsigned
) returns varchar(10000) no sql
begin
    declare result varchar(10000) default content;
    if char_length(content) > max_length then
        set result = left(content, max_length);
        set result = concat(result, '……');
    end if;
    return result;
end $$

delimiter ;
```

> **Note 1**: `no sql` after the function declaration says that the function body does not execute SQL statements. If the body needs to read data with SQL, it should usually be declared as `reads sql data`.
>
> **Note 2**: The `delimiter` command before and after the function definition changes the statement terminator. Because the statements inside the function body end with `;`, you need another delimiter while defining the function, otherwise the code would be cut off and executed too early.

Call the function in a query:

```SQL
select fn_truncate_string('Walk with me through the streets of Chengdu until all the lights go out and we still do not stop', 10) as short_string;
```

```
| short_string   |
+----------------+
| Walk with m……  |
+----------------+
```

### Procedures

A stored procedure is a collection of SQL statements compiled in advance and stored in the database. Calling a procedure can simplify the work of application developers, reduce communication with the database server, and improve the performance of data operations. Up to now, all of the SQL we have written has been a single statement operating on one or more tables, but in real development it is common to run into operations that require several SQL statements to complete.

For example, when an e-commerce site processes a user order, it may need to do the following:

1. Check whether inventory exists and whether it is sufficient.
2. Lock inventory and decrement available stock.
3. If stock is insufficient, contact suppliers or generate warning records.
4. Write logs and create user notifications regardless of success or failure.

We can package these complex operations into a procedure. That not only helps guarantee data consistency, but also means that if the business rules change later, we only need to adjust the procedure. For the caller, the procedure does not expose the details of the underlying tables, and executing a stored procedure is much faster than sending the same group of SQL statements one by one.

The following procedure performs a salary increase in the `hrs` database:

- Department `10`: add `300`
- Department `20`: add `800`
- Department `30`: add `500`

```SQL
delimiter $$

create procedure sp_upgrade_salary()
begin
    declare flag boolean default 1;
    declare continue handler for sqlexception set flag=0;

    start transaction;
    
    update tb_emp set sal=sal+300 where dno=10;
    update tb_emp set sal=sal+800 where dno=20;
    update tb_emp set sal=sal+500 where dno=30;

    if flag then
        commit;
    else
        rollback;
    end if;
end $$

delimiter ;
```

> **Note**: The procedure above uses `start transaction` to open a transaction scope. To determine whether an exception occurs and therefore whether the transaction should be committed or rolled back, the procedure defines a variable named `flag` and an exception handler. If an exception occurs, `flag` is set to `0`, and the later branch decides whether to execute `commit` or `rollback`.

Call the procedure:

```SQL
call sp_upgrade_salary();
```

Drop the procedure:

```SQL
drop procedure if exists sp_upgrade_salary;
```

Inside a stored procedure, you can define variables and conditions, use branching and loop statements, operate on query results through cursors, and even use the event scheduler. We will not go into those topics here. Although procedures do have advantages, in real development, using procedures heavily and placing too much complex computation inside them can put enormous pressure on the database server. The database is often already the performance bottleneck, so that would only make things worse. For internet products, it is usually better to let the database focus on storage and leave complex computation and processing to programs running on the application server. If the application server becomes overloaded, it is usually much easier to deploy more application servers and share the pressure.

If you are interested in views, functions, procedures, or even triggers, which we did not cover here, a general introductory book such as *MySQL Crash Course* is enough for a broad understanding. In many jobs you may never use these features heavily; often people study them mostly because they may come up in interviews.

### Additional Topics

#### Normal Forms

Normal form theory provides guidance for relational schema design.

1. First Normal Form: every column value must be atomic.
2. Second Normal Form: every non-key attribute must fully depend on the key.
3. Third Normal Form: non-key attributes should depend only on candidate keys, not on each other.

> **Note**: In real work, for efficiency reasons, we may intentionally introduce denormalization when designing tables, that is, we deliberately lower the normal form and add redundant data in exchange for better performance.

#### Data Integrity

1. Entity integrity: each entity is unique.
   - `primary key`
   - `unique`
2. Referential integrity: relationships cannot reference nonexistent rows.
   - `foreign key`
3. Domain integrity: data must be valid.
   - proper data type and length
   - `not null`
   - `default`
